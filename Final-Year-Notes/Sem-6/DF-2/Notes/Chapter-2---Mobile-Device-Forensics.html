Chapter 2: Mobile Device Forensics

Subject: Digital Forensics-2 (CDS-361) Semester: Sem 6 Tags: forensics mobile android evidence-acquisition

2.1 Need and Challenges (2024)

Mobile devices are the central repository of personal data (Location, Chat, Health). However, forensics is increasingly difficult due to:

  • Encryption: Modern Android uses File-Based Encryption (FBE). Data cannot be accessed without the passcode or high-level exploits (e.g., GrayKey, Cellebrite Premium).
  • OS Fragmentation: Thousands of device models with customized OS versions (MIUI, OneUI) require specific bootloaders/exploits.
  • Anti-Forensics: Features like “Auto Factory Reset” after wrong attempts and Secure Folder/Second Space.

2.2 Mobile Architecture & File System

Android is built on the Linux Kernel.

Key Partitions

  1. /system: Read-only partition containing the OS and pre-installed apps. Forensically less interesting unless looking for malware persistence.
  2. /data: The Gold Mine. Contains specific user data:
    • /data/data/: App directories (Databases, Shared Preferences).
    • /data/misc/: WiFi keys, VPN configs.
  3. /cache: Temporary files, OTA updates, and recovery logs.

File Systems

  • ext4: Standard Linux file system. Supports “Journaling” (helps recover some data).
  • F2FS (Flash-Friendly File System): Optimized for flash storage, widely used by Samsung. Harder to carve deleted data from than ext4.

2.3 Acquisition Processes

There are three main levels of data extraction:

2.3.1 Manual Acquisition

  • Method: Manually browsing the phone and taking photos/screenshots of the evidence.
  • Use Case: When the device cannot be connected to a PC (e.g., damaged port) or strict privacy laws prevent full imaging.
  • Pros: Simple, visual.
  • Cons: Misses hidden/deleted data; difficult to search.

2.3.2 Logical Acquisition (ADB)

  • Method: Extracts data accessible to the user via API (Standard Backup).
  • Tool: ADB (Android Debug Bridge).
    • Command: adb backup -apk -shared -all -f backup.ab.
  • Use Case: Unrooted phones where physical extraction isn’t possible.
  • Pros: Fast, universally supported.
  • Cons: Cannot access protected app data (e.g., WhatsApp DBs) if the app disallows backup.

2.3.3 Physical Acquisition

  • Method: Bit-by-bit copy of the flash memory (NAND). Creates a dd image (e.g., mmcblk0).
  • Requirement: Usually requires Root Access or a Bootloader Exploit (EDL Mode).
  • Techniques:
    • JTAG/ISP: Connect directly to motherboard test points (Hardware intensive).
    • Chip-Off: Desoldering the storage chip (Destructive, last resort).
  • Pros: Recovers Deleted Data from unallocated space.
  • Cons: Risk of bricking the device; expensive equipment.

2.4 Android Data Analysis

Once extracted (usually logically via ADB/Agent or Physically via Image), analysis involves parsing databases.

Key Artifact locations:

  • SMS/MMS: /data/data/com.android.providers.telephony/databases/mmssms.db
  • Contacts: /data/data/com.android.providers.contacts/databases/contacts2.db
  • Call Logs: /data/data/com.android.providers.contacts/databases/calllog.db
  • WhatsApp: /data/data/com.whatsapp/databases/msgstore.db (Encrypted, needs key).

Tools

  1. Autopsy: Best open-source tool. Can parse Android Backup (.ab) and Raw Images.
  2. Cellebrite UFED Physical Analyzer: The industry leader for decoding complex apps.
  3. SQLite Browser: Essential for manually inspecting .db files extracted from the phone.

Deleted Data Recovery

  • File Carving: Searching the “Unallocated Space” of a physical image for headers/footers (e.g., looking for FF D8 ... FF D9 for JPEGs).
  • SQLite Wal/Journal: Uncommited transactions in Main Database files often contain “deleted” records that haven’t been overwritten yet.

Q: Which tool/method to create image of phone data, and why?

  • Logical (ADB backup): adb backup -apk -shared -all -f backup.ab — fast, no root, but misses deleted data
  • Physical (dd via ADB root shell): adb shell dd if=/dev/block/mmcblk0 | dd of=android.img — full bit-for-bit, recovers deleted data, needs root
  • Autopsy: Load .ab or raw image → automated artifact parsing
  • Why physical preferred: Only method that recovers deleted data from unallocated space

Q: How to use Autopsy to analyze Android image? File recovery options?

  1. Open Autopsy → New Case → Add Data Source → select image file
  2. Select ingest modules: Android Analyzer, File Type Identification, Keyword Search
  3. Autopsy parses: SMS (mmssms.db), Contacts (contacts2.db), Call logs, Browser history
  4. File Recovery options:
    • Data Artifacts → shows parsed app data
    • Deleted Files → lists carved deleted files from unallocated space
    • File Type → filter by images/video/audio
    • Right-click any file → Extract

Q: Extract and analyze call logs from mobile image

  • DB path: /data/data/com.android.providers.contacts/databases/calllog.db
  • Open with SQLite Browser → table calls → columns: number, date, duration, type (1=incoming, 2=outgoing, 3=missed)
  • In Autopsy: Data Artifacts → Call Logs

Q: Recover deleted data from mobile image

  1. Physical image required (logical won’t have unallocated space)
  2. File Carving: Autopsy or Foremost scans for JPEG FF D8, PNG 89 50 4E 47 etc.
  3. SQLite WAL: Check -wal and -journal files alongside .db files — contain uncommitted (deleted) rows
  4. Autopsy: Deleted Files view shows recovered entries

Q: Recover deleted SMS messages — tools + integrity verification

Tools: Autopsy, Cellebrite UFED Physical Analyzer, SQLite Browser Steps:

  1. Extract mmssms.db + mmssms.db-wal / mmssms.db-journal
  2. Open in SQLite Browser → check sms table — deleted rows may still be in WAL
  3. Hash the DB before and after (md5sum mmssms.db) to prove integrity
  4. In Autopsy: Data Artifacts → Messages

Q: What permissions required for ADB system-level access?

  • USB Debugging must be enabled (Developer Options)
  • For /data access: Root required (or bootloader unlock + custom recovery)
  • Physical acquisition (dd of full partition): Root shell via adb root
  • No special OS permissions needed for logical backup on user partition

Q: Security risks of enabling ADB

  • Full shell access to device over USB
  • Silent app install/uninstall (adb install malicious.apk)
  • Data exfiltration (adb pull)
  • Credential theft if connected to untrusted computer
  • Bypass screen lock on some older Android versions
  • Mitigation: Disable after use, always authorize only known computers

Q: Recover contacts via Google account — steps + limitations

Steps:

  1. Go to contacts.google.com → Settings → Undo changes
  2. Select restore point (up to 30 days back) → Restore
  3. Alternative: Google Account → Data & Privacy → Google Takeout → export Contacts

Limitations:

  • 30-day window only
  • Only synced contacts recoverable — locally stored contacts lost
  • Contacts deleted before sync-to-Google are unrecoverable this way
  • No fine-grained per-contact restore — full rollback only

Q: Security/privacy concerns when recovering deleted mobile data

  • Recovered data may contain third-party private info (other people’s messages)
  • Legal authorization (warrant/consent) required before extraction
  • Chain of custody must be maintained — hash image before and after
  • Sensitive data (banking, health) must be handled per IT Act / PDPB compliance
  • Risk of re-victimization if victim’s intimate data is exposed during investigation
